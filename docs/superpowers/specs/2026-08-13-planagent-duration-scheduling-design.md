# PlanAgent 预期完成时长与均匀排程设计

## 目标

把首页的绝对日期输入改为“数值 + 天/周/月”预期完成时长。后端以收到请求当天为计划开始日，包含周末，将 LLM 生成的全部任务按顺序均匀铺到该时长内。LLM 继续只决定计划内容，不生成任何日期。

## 用户交互

首页使用一个正整数输入框和一个单位选择框：

- 数值默认 `30`，最小值为 `1`。
- 单位可选 `天`、`周`、`月`，默认 `天`。
- 提交字段为 `duration_value` 和 `duration_unit`，不再由首页提交绝对 `target_date`。
- 创建成功后的导航和其余页面行为保持不变。

## API 与兼容性

`POST /api/goals` 新增两个可选字段：

```json
{
  "title": "学习 Python",
  "description": "完成一个项目",
  "duration_value": 3,
  "duration_unit": "month"
}
```

`duration_unit` 只接受 `day`、`week`、`month`。数值必须为正整数。两个字段必须同时提供或同时省略。

现有 `target_date` 字段继续保留，以兼容旧客户端；新时长字段与 `target_date` 不允许同时提交。通过时长创建目标时，服务端计算出的绝对截止日期仍保存到 `Goal.target_date`，现有响应 DTO 与数据库结构无需变化。

如果没有提供时长但提供了旧式 `target_date`，服务层在今天至目标日期之间使用同样的均匀排程。如果两个字段都没有提供，则保留现有按每日容量尽快安排的行为。

## 时长换算

服务端只取一次 `date.today()`，并将该值同时用作计划开始日和所有日期计算的基准，避免跨午夜时各层得到不同日期。

- `N day`：截止日为开始日加 `N` 天。
- `N week`：截止日为开始日加 `7 × N` 天。
- `N month`：按日历月增加 `N` 个月，尽量保留日号；目标月份没有该日时截断到该月最后一天。例如 `2026-01-31 + 1 month = 2026-02-28`。

截止日早于开始日时返回请求校验错误，不创建 Goal。

## 均匀排程算法

均匀模式不使用 LLM 的日期偏移，也不跳过周末：

1. 按里程碑在 `PlanSpec` 中的顺序、再按任务在里程碑中的顺序，将任务展平成一个序列。
2. 没有任务时返回空排程。
3. 只有一个任务时安排在开始日。
4. 有多个任务时，令任务数为 `n`、开始日至截止日的自然日差为 `span_days`。第 `i` 个任务的日期偏移为 `round(i × span_days / (n - 1))`，其中 `i` 从 `0` 到 `n - 1`。
5. 因此首任务一定在开始日，末任务一定在截止日，中间任务保持原顺序并尽量等距。任务数多于可用日期时，允许多个相邻任务安排在同一天。

任务的 `effort_hours` 仍被持久化，但均匀模式按任务节点分布，不改变或拆分 LLM 生成的任务。无截止日模式继续使用现有 `blocks_per_day` 与 `hours_per_block` 容量算法。

## 里程碑日期

均匀模式下，每个里程碑的 `due_date` 取该里程碑最后一个已排程任务的日期。没有任务的里程碑使用总目标截止日。这样所有里程碑日期都由确定性算法产生，且不会晚于 `Goal.target_date`。

无截止日模式继续使用 LLM 给出的 `target_date_offset_days` 计算里程碑日期，以保持兼容。

## 错误处理

- 非正整数、未知单位、只提供一个时长字段、同时提供时长和绝对日期：FastAPI/Pydantic 返回 `422`。
- 旧式截止日期早于今天：返回 `422`。
- LLM 或持久化异常继续由现有 Goals API 转换为 `502`，并由服务事务回滚，不遗留孤立 Goal。

## 测试策略

后端测试覆盖：

- 天、周、月换算及月末截断。
- 均匀排程的首尾日期、中间等距、包含周末。
- 单任务、任务多于日期数、空计划。
- duration API 校验、计算后 `Goal.target_date` 持久化。
- 里程碑日期取最后任务日期。
- 未提供截止日时的现有容量排程不回归。

前端验证覆盖 TypeScript/Vite 构建，并检查提交 payload 使用正整数 `duration_value` 和受限的 `duration_unit`。后端全量 pytest 与前端 build 都必须通过。
