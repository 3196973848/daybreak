# 自适应每日任务拆解与时间容量排程设计

日期：2026-08-13

## 目标

创建目标时由用户填写预期完成时长和每日可投入时间。每日可投入时间默认 2 小时。模型自行识别目标涉及的领域、知识结构和复杂度，把宽泛任务拆成可在一天内完成的原子任务；后端再按照每日时间容量，把任务在包含周末的整个预期周期内均匀铺满。

例如“学习交易规则”不作为一个宽泛的每日任务直接落库，而应按目标上下文拆成交易时段与休市、订单类型与成交机制、涨跌停与熔断、保证金与强平、费用与结算等具体子知识点。

## 不使用 LangGraph

本功能不引入 LangGraph。流程只有“生成结构化计划 → 校验粒度和容量 → 必要时带反馈重新生成”这一条有限循环，普通 Python 函数即可清晰表达并完整测试。引入状态图会增加依赖、启动成本和维护面，却不会改善当前结果。

以后只有在计划生成发展为多代理协作、人工审批、可中断恢复或多分支工作流时，再单独评估 LangGraph。

## 创建目标输入

前端在“预期完成时间”下增加“每日可投入时间”数值输入：

- 默认值为 2 小时。
- 必须为正数，并以 0.5 小时为步长。
- API 字段名为 `daily_hours`。
- 新前端始终提交该字段；后端默认值仍为 2，以兼容旧客户端。
- 该值用于本次计划生成、容量校验和排程。当前不新增数据库字段；任务本身已保存预计耗时，目标周期已保存截止日期，可从最终计划还原排程结果。

## 模型自行识别领域与粒度

模型直接输出原子任务，不先生成大任务再逐项进行第二轮拆解：

1. 根据目标识别领域或阶段，并将它们作为里程碑。领域数量由目标实际需要决定，不使用固定类别表。
2. 在每个领域内识别必要的知识点、技能或交付步骤。
3. 每个任务必须有具体动作、明确范围和可验证成果，不得使用“学习某领域”“掌握相关知识”“完成项目”等宽泛标题。
4. 每项任务估算 `effort_hours`，以 0.5 小时递增，最少 0.5 小时，且单项不得超过用户的 `daily_hours`。
5. `type` 继续使用 `learn`、`practice`、`project`；模型根据任务性质自行选择。
6. 模型只决定领域、内容、顺序、类型和预计耗时，不能输出任何具体日期。

服务端在提示词中包含目标周期和每日时间预算，并明确要求按上述规则生成。一次调用产生完整计划，避免两阶段调用带来的额外费用、延迟和结构漂移。

## 结构校验与重新生成

后端对模型结果执行以下校验：

- 里程碑和任务非空，顺序稳定。
- `effort_hours` 是 0.5 的正数倍。
- 任一任务的耗时不超过 `daily_hours`。
- 任务标题和描述不为空。
- 任务中不含模型分配的日期字段；现有 schema 继续不接受日期。

结构或粒度校验失败时，将具体失败原因反馈给模型并最多重新生成 2 次。三次均失败则返回明确错误，不创建 Goal，不留下半成品数据。

后端可以可靠校验结构、时间和容量，但“标题是否足够具体”主要由提示词约束；不使用脆弱的关键词黑名单替代语义判断。

## 时间容量与不足提示

预期周期按当前含开始日的自然日语义计算。总容量为：

`自然日数量 × daily_hours`

周末计入自然日和容量。模型计划的总预计时间为所有原子任务 `effort_hours` 之和。

后端同时检查总预计时间是否超过总容量，以及按顺序装箱形成的工作组数量是否超过周期自然日数。后者处理任务不可拆分造成的容量碎片，例如每天 2 小时、任务依次为 1.5/1.5/1 小时时，虽然总计 4 小时，但仍需 3 个工作日。任一检查不通过时，后端不强行把任务塞进日期，也不创建目标。API 返回可识别的容量不足错误，包含：

- `required_hours`：计划总预计小时数。
- `available_hours`：当前周期可用小时数。
- `minimum_days`：`ceil(required_hours / daily_hours)` 与实际工作组数量的较大值。
- `suggested_duration`：以“天”为单位的建议预期时长。

前端展示：“当前时间不足：计划约需 X 小时，现有周期可用 Y 小时。建议至少设置 Z 天，或提高每日投入时间。”用户修改后重新生成。

无截止日期的旧 API 请求仍沿用现有容量优先排程，不改变兼容行为。

## 容量分组与均匀铺满算法

有截止日期时，排程分两步执行：

### 1. 按每日时间预算形成工作组

按里程碑和任务顺序展平任务，使用顺序装箱：

- 从第一个任务开始累加 `effort_hours`。
- 加入下一个任务会超过 `daily_hours` 时，关闭当前工作组并开始新组。
- 不拆分一个原子任务；模型已保证单项能够在一天内完成。
- 每个工作组代表同一天可以完成的一组任务，组内任务保持原始顺序。

### 2. 把工作组均匀映射到整个周期

设工作组数量为 `G`，周期自然日数为 `D`。容量校验保证 `G <= D`。

- 无任务时返回空排程。
- 只有一个工作组时安排在今天。
- 多个工作组时，第 `i` 组映射到 `round(i × (D - 1) / (G - 1))` 对应的自然日。
- 因此首组在今天、末组在截止日，中间组均匀分布；周末不跳过。
- 同一工作组的多个原子任务安排在同一天，所以复杂领域可自然出现“一天多个子知识点”。
- 每日累计耗时永远不超过 `daily_hours`，任务和里程碑顺序保持不变。

里程碑截止日继续等于该里程碑最后一个任务的日期，并且不晚于目标截止日。

## API 与错误契约

`POST /api/goals` 在现有时长字段之外接受：

```json
{
  "duration_value": 30,
  "duration_unit": "day",
  "daily_hours": 2
}
```

`daily_hours` 接受正的 0.5 倍数，拒绝布尔值、字符串、零、负数、非 0.5 倍数和非有限数。无效输入返回 422，且不会调用模型。

容量不足使用独立、结构化的 422 响应，前端可直接读取建议值。模型调用或输出在重试后仍失败则返回 502。数据库事务覆盖 Goal、Plan、Milestone 和 Task 的完整创建过程，任何失败均回滚。

## 测试

后端覆盖：

- `daily_hours` 的默认值和严格输入校验。
- 提示词包含每日预算、自主领域识别、原子任务和禁止日期要求。
- 0.5 小时粒度、单项上限和无效计划重试。
- 总容量边界：恰好装满通过，超过 0.5 小时即返回结构化不足提示并回滚。
- 顺序装箱后同日多任务、每天不超预算、工作组均匀铺满、包含周末、首末组边界和跨里程碑顺序。
- 无截止日期的旧容量模式保持原行为。

前端覆盖：

- 显示每日投入时间，默认 2 小时，步长 0.5。
- 非法值的可访问错误提示。
- 创建请求携带 `daily_hours`。
- 容量不足时显示所需、可用和建议天数。

最终验证包括完整后端测试、前端测试、生产构建及 `git diff --check`。
